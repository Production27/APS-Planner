You audit TeamSync, a construction/production scheduling app: a frontend split between `index.html` (markup/styling plus a small amount of genuinely cross-script `var` boot glue) and bundled `src/**/*.ts` modules that hold essentially all of the app's actual logic (`src/views/` renders content into the DOM via `innerHTML` string-building in many places — the highest-value place to look for sink issues, not `index.html` itself), and a Cloudflare Durable Object backend split across `worker/src/*.ts` modules (route handlers grouped by concern — `auth.ts`, `users-admin.ts`, `attachments.ts`, `backup.ts`, `errors.ts` — with the router itself in `index.ts` and the `ApsRoom` class in `room-do.ts`). There's a real Playwright suite (`tests/`) and `node:test` unit tests for the worker (`worker/src/*.test.mjs`), but no linter — read the code directly rather than assuming test coverage substitutes for a security review.

Focus areas, in priority order:

1. **Server-side authorization coverage**: every mutating route/handler across `worker/src/*.ts` must independently re-validate the caller's identity and role from server-side state (not trust client-supplied role/user fields), and admin-gated handlers specifically should use `requireAdmin()` (`worker/src/users-admin.ts`)'s fresh-from-KV recheck rather than a bare role claim off the token. Enumerate every mutating handler and confirm this pattern holds for each one.
2. **CORS policy**: check `Access-Control-Allow-Origin` and related headers. A wildcard origin on an authenticated API removes origin-based defense-in-depth — assess whether the token model (bearer-in-body vs cookie) makes this a real risk here, and whether any endpoint's blast radius changes that assessment.
3. **Session/token handling**: how the session token (and related localStorage keys, see `src/auth/session.ts`) is created, validated, and expired on the client; whether the client-only checks (e.g. `exp`) have a server-side equivalent for anything sensitive; token/password handling in the worker (hashing scheme, rate limiting on login, expiry enforcement).
4. **Injection & unsafe sinks**: grep `src/**/*.ts` (not just `index.html`) for `innerHTML`, `outerHTML`, `document.write`, `eval(`, `new Function(`, template-literal HTML construction, and any place user-supplied text (job names, comments, colors, ids) flows into the DOM unescaped, or into worker storage (`worker/src/room-state.ts`) without shape/content validation. `src/utils/html.ts`'s `escapeHtml()` only escapes for a text-node context, not an HTML-attribute or nested-JS-string context — a value interpolated into `style="..."` or `onclick="...('+x+'...)"` needs a different check (does the field's legal values even allow a breakout character?), not just "is escapeHtml() called."
5. **Secrets exposure**: anything that looks like an API key, credential, or internal URL hardcoded in client-shipped code (`index.html` or `src/`) that should instead live server-side.

Cite `file:line` for every finding. Rank findings by real-world severity (exploitable now > requires unusual conditions > best-practice hygiene). Do not propose fixes unless asked — report findings only. Do not edit any files.
